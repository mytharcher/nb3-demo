# 六步骤评审与应用管理实施计划与模块任务

版本：V1.0  
日期：2026年10月29日  
需求基线：[六步骤评审与应用管理 PRD V2.0](./六步骤评审与应用管理_PRD_V2.0.md)（含2026年10月29日待确认补充）  
用途：供协调 agent 分配任务，开发 agent 实施，测试 agent 追踪验收。

## 1. 使用方式与实施边界

本计划覆盖投稿、上级审核、AI评分、专家复议、人工兜底、结果确认、公示、门户、看板及配套管理功能。只拆分工作，不表示业务决策已经批准，也不表示任务已经开始。所有任务初始为“待领取”，负责人均待分配。

接手任务时先读对应 PRD 章节、本任务卡、前置任务交接记录及项目 [AGENTS.md](../AGENTS.md)。以任务 ID 为分配与验收单位；模块负责人可以承担多个任务，但不得因为分配了某模块而修改其他模块的业务规则。

- 第13章 DEC-01～DEC-13 全部保持“待确认”。下文引用的补充行为都是相应 DEC 获批后的实施目标；涉及推荐数值的实现可以先做配置结构、契约、测试夹具，但不能静默作为生产默认值启用。
- 已确认的主体流程继续有效。正文受第13章调整的部分同样受决策门禁约束。发现冲突由 M00 留痕并取得业务结论，不由开发 agent 自行选择。
- 原 PRD 保持不变；后续批准的变更须记录决策版本、确认人、日期、结论及受影响任务、测试，必要时再同步需求基线。
- 本期不建设 OA 主流程、常规大众评委、奖金发放、专家结算、任意回退或删除历史、跨设备投稿草稿、课程学习进度同步、完整移动端评审。
- 估算与排期在契约、审批能力、业务资料确认后由协调人补充。本计划使用依赖和里程碑，不承诺缺少人员与集成信息时的日历工期。

## 2. 项目现状与技术约束

### 2.1 已核实的起点

截至本计划编写时，应用为 NocoBase 3 默认模板起点，`package.json` 的模板版本为 `1.0.0-beta.84`。`client/routes.ts` 主要为首页、收件箱和认证页面；用户及角色管理已有准备代码，尚未在应用路由注册。应用业务库迁移尚未包含六步骤业务表。

| 能力                   | 当前依据与实施要求                                                                                                                                       |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 登录、用户、权限       | 客户端和服务端已注册 authentication、users、authorization 及权限规则插件；复用插件，不另造账户或权限系统                                                 |
| 文件、消息、调度、邮件 | 已注册 file、notification、notification-in-app、scheduler、mail；注册不等于存储、扫描、邮件服务已经可用，须逐项验证配置与接口                            |
| 生命周期及异步任务     | 已依赖 lifecycle、jobs、queue；投稿状态采用应用生命周期，外部调用使用提交后的 effect/任务，不在数据库事务内调用 AI 或邮件服务                            |
| 提交保护               | 已有 submission provider；业务写操作复用 operation key 和 receipt 事务机制                                                                               |
| 流程管理 UI            | 模板提供生命周期图和 workflow-management 扩展；应复用定义目录、参数编辑和授权执行历史                                                                    |
| 审批插件               | 未在依赖或注册表发现 `@nocobase/app-plugin-approval`；该能力为商业 Pro 插件，需要相应授权及兼容版本。M00-02 先评估并推荐安装，不能假定已有能力或编造 API |
| AI及组织集成           | 尚未确定真实评分服务、组织关系来源、正式评分资料；先定义适配边界，测试替身不得冒充生产完成                                                               |

### 2.2 所有任务共同遵守

1. 业务代码直接放在应用目录，不为每个模块新建插件。开发前读项目内 `nocobase-app-development` Skill，再按任务读取数据库、授权、文件、通知、调度等对应 Skill。
2. 页面懒加载并默认导出，使用 `defineAppRoutes()`、稳定页面 ID、`navigation` 和 `authz`；路径不写 `/main`。业务列表复用 DataTable，基础 UI 使用已有 shadcn 组件和语义主题 token，文案写入应用中英双语 locale。
3. API 采用 camelCase 路径、`{ data }` 成功体、`ApiError`、`apiValidator()`、`describeRoute()`；每个路径独立认证授权。页面权限、动作权限、记录范围分别设计；附件、导出、聚合同样检查记录范围。
4. 已有插件端点从运行应用 API 文档发现；需凭据时使用用户提供的 API key 或已有会话，不自行创建 key。插件注册/Collection 变化后重新获取 API 文档。
5. 状态只由生命周期转换；已发布标准、文件、批次、原始评分、公示快照不可覆盖。迁移自包含且 `down` 明确；已合并迁移不改写，生成的 collections 不手改。
6. 业务角色仅显式分配给指定用户，通过用户管理可查看及撤销；不向 `authenticated:*` 或平台 member 扩大业务权限。多角色不能绕过回避规则。
7. 每个模块同时交付用户界面、所需管理界面、API、权限、审计和失败恢复；不能用空菜单或假成功代替真实能力。
8. 只运行受影响范围的格式、lint、类型检查和测试；测试放 `tests/`，页面测试复用现有 harness。运行地址只采用 `pnpm dev` 输出的 `Local:` URL。

### 4.3 跨模块契约最低要求

M00-03 与 M01-01 共同输出数据字典、OpenAPI/DTO、事件字典及权限矩阵。以下是必须保留的语义，不是已经存在的 API 或物理表名。

| 契约       | 必须固定的内容                                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------------------------------- |
| 投稿标识   | `submissionId`、原周期/月份、原参与者、历史部门、当前批次、当前轮次、主状态、评分方式、有效性、并发版本           |
| 材料与标准 | `batchId`、不可变 `fileVersionId`、模板版本、`roundId`、`ruleVersionId`；技术重试沿用同一组引用                   |
| 结果       | `resultVersionId`、原AI分、当前有效分、最终确认分、来源与精度；人工兜底无虚构逐项评分                             |
| 专家       | `reviewInstanceId`、处理类型、三席位、`assignmentVersion`、撤销/提交有效性；明确未公开意见的响应字段过滤          |
| 写命令     | operation key、expected version、操作者、授权上下文；相同 key 和相同请求返回原结果，复用 key 但请求内容不同应拒绝 |
| 并发失败   | 状态已变/版本冲突/权限撤销均有稳定错误码与最新状态刷新策略；不得把失败显示为成功                                  |
| 事件       | 事件ID、聚合ID、轮次/结果版本、动作、发生时间、接收对象、去重键；消费前重查有效性                                 |
| 通知回执   | 业务事件到站内送达状态的可查询关联；M09 可判断是否需要暂停或重设自动确认期限                                      |
| 公示       | 批次类型、原投稿月份、结果/奖项/模板/内容/收件快照版本、确认版本、每人投递状态                                    |
| 更正影响   | 失效原因、旧新版本关系、需关闭待办/冻结发送/刷新统计的对象集合；保留历史证据                                      |

建议领域命令包括提交/重提、审核通过/退回、评分恢复/转人工、分配/替换专家、提交专家结果、确认/异议、公示确认/发送、更正申请/批准。最终 HTTP 路径及 DTO 在 M00-03 冻结，不能凭本表假定插件存在同名接口。

必须保证：保存有效 AI 结果、阈值判断、创建自动复议及主状态更新为同一事务；专家最终聚合与结果转换为同一事务；确认与冻结最终分为同一事务；业务提交与补交授权消耗为同一事务。外部通知/AI/邮件在提交后执行并保留可恢复投递记录。

## 7. Agent 执行与交接规则

### 7.1 领取顺序

1. 协调者明确任务 ID、负责人、文件边界、依赖契约版本及允许修改的共享文件。没有授权的共享文件变更先提交变更请求。
2. 开发者检查任务涉及的 DEC 和业务资料。缺资料则完成不受影响的契约/结构/测试并记录阻塞，不擅自选生产规则；不得宣布整个模块完成。
3. 新建业务 UI 前先读项目 frontend workflow，按其要求完成设计与验收流程；调用插件前读对应 Skill。审批插件未具备时，继续独立任务，不编造接口或替代引擎。
4. 完成实现、模块管理面、权限、国际化及测试，再提交协调者联调。接口变更先通知消费者并更新契约。
5. 协调者按依赖顺序集成共享入口；测试者用独立角色与真实权限重跑受影响链路后标记完成。

### 7.2 状态与完成定义

任务状态：待领取 → 进行中 → 待联调 → 待验收 → 已完成；阻塞单独记录“阻塞原因/等待谁/解除条件/已完成部分”。开发完成不等于业务验收完成。

完成必须满足：任务范围实现，获批规则一致，相关管理面可操作，页面及动作权限生效，版本/幂等/历史留存正确，中英文文案完整，相关自动化与真实集成检查有证据，无未披露阻塞。需要业务、技术或运维签字的门槛尚未批准时保持待验收。

### 7.3 交接模板

每个任务在协调记录中填写以下内容，便于其他 agent 直接接续：

```text
任务 ID / 模块：
负责人 / 当前状态：
需求条目 / DEC批准版本 / 契约版本：
已实现行为与边界：
修改文件及共享文件变更请求：
新增 API / DTO / 事件 / 权限动作：
数据迁移顺序、回滚及历史数据影响：
依赖服务与配置项（不记录密钥）：
验证命令、范围、结果及证据路径：
真实集成与测试替身的区别：
未完成项、阻塞责任人和解除条件：
下游可开始任务 / 需重验任务：
```

权限初始化变化必须执行 `pnpm exec vitest run tests/server/authorization-assignment-safety.test.ts`；涉及页面权限标签运行 `tests/client/page-permission-titles.test.ts`。其余测试由任务选择具体文件，不把全应用 `pnpm check` 作为每次提交的例行步骤。

## 8. 最终交付门禁

- **业务基线**：DEC及正式评分规则、模板、组织、日历、专家池、案例和公示资料已由对应责任人批准；推荐值没有无记录启用。
- **业务闭环**：普通AI、极端分自动复议、用户异议、人工兜底、更正均从原投稿追溯到最终结果；无管理员代评分/常规代确认，无未授权状态捷径。
- **管理完整**：用户与角色、周期/补交、规则、专家池/分配、AI异常、流程、通知/调度、公示/获奖、模板/门户、日历/运行参数、审计/更正具备真实可操作界面。
- **安全与一致性**：普通用户、多角色、停用、撤销专家、直接下载/接口/聚合均验证；重复、并发、迟到回调和发送未知状态有明确处理。
- **真实服务**：插件授权、组织、存储/安全扫描/预览、AI、站内通知及邮件经过目标环境验证；模型/提示词等变更有参考集回归。
- **运行保障**：批准的容量、性能、浏览器和恢复目标通过；数据库及文件联合恢复成功；有上线、回退、监控责任和故障恢复步骤。
- **证据完整**：任务与 SUB、原验收、AC 可双向追溯；未验证行为明确列示，不以 mock、截图或菜单存在代替功能验收。
